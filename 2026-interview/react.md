# react 面试题
### 1. JSX本质是什么，为什么浏览器无法直接解析 JSX？
JSX(JavaScript XML),Javascript的0拓展语法，因为浏览器支持的是 ECMAScript 规范，所以它并不支持直接解析 JSX 语法，react中需要插件配合将JSX语法编译成浏览器识别的 ECMAScript 语法规范，比如：babel-preset-react。
### 2. React哲学：UI=f(state)
核心思想解释：
1. 函数f(组件)计算出来的结果
2. 自动售货机，投入特定的"硬币"(status)，它就一定会吐出特定的"饮料"(UI)
精炼定义：
UI=f(state)精辟地概括了 React 的核心设计哲学，用户界面是应用状态的纯函数映射结果
逐一解释公式：
1. state：单一数据源，驱动 UI 变化的唯一事实来源
2. f:(函数)组件，根据state(和props)返回 UI 描述
3. UI: 虚拟DOM,对 UI 的一种轻量级描述
### 3. 虚拟DOM
核心定义：虚拟DOM(Virtual DOM)本质上是一个普通javascript对象。
描述内容：它用来描述真实网页中DOM树的结构和属性。
形象比喻：可以看作是真实DOM的一个"蓝图"或"快照"。
关键特性：轻量级，存在于内存中，操作成本低。
核心原因：解决直接操作真实DOM可能带来的性能瓶颈。
直接操作DOM的后果：大量连续的重排和重绘，导致页面卡顿，用户体验下降。 

易错点：虚拟DOM并非总是更快
原因分析：
简单应用或开发者能精确优化DOM操作时，直接操作可能更快。虚拟DOM自身有JS计算开销
虚拟DOM的真正优势：
1. 为复杂、动态、数据驱动应用提供声明式、易维护的UI更新方案
2. 保证多数复杂场景下有相对不错的性能下限
3. 用一定计算开销获取开发效率大幅提升和代码可维护性增强

虚拟DOM的Diff算法工作原理：
核心三大策略
1. 同层比较：只比较新旧虚拟DOM树中统一层级的节点，不会跨层级对比。
2. 类型检查：若两个节点类型不同（如<div>变<span>），直接销毁旧节点及子树并重建新节点，不继续深入比较。
3. key属性：列表渲染时必须使用稳定唯一的key(如id),帮React识别节点身份，避免用索引 index。
子节点"双端对比"流程
这是最复杂的部分，主要处理可复用节点，经历两轮遍历：
1. 第一轮(从左向右)：依次对比新旧列表的头节点。若节点key和类型都匹配则复用并继续；若不匹配则立即跳出循环。
2. 第二轮（处理剩余）：将第一轮剩下的就节点存入 Map 映射表。遍历剩下的新节点，若key在映射表中存在则移动位置复用；若
   不存在则新增。最后，删除映射表中未被匹配的就节点。

虚拟DOM的缺点或适用边界？
1. 额外的JavaScript计算开销
2. 首次渲染的轻微延迟
3. 内存占用

### 4. vite和webpack
传统构建：webpack的工作模式
核心思想：一切皆模块
1. 从入口点递归构建以来图
2. 将所有模块打包成一个或多个 bundle 文件
问题：开发模式下的瓶颈
1. 漫长的启动阶段
开发服务器启动时需要完成整个项目的遍历、依赖分析、编译和打包，结果大型项目启动非常慢（数秒至数十秒）
2. HMR 的优化空间
文件变化时，任然需要判断影响模块并重新构建
复杂项目中，HMR 响应速度可能不尽如人意。

vite构建的优势：
1. 开发时不打包，按需服务
启动及服务：Vite开发服务器几乎瞬间启动，无需预打包
工作方式：
源码通过浏览器支持的 <script type="module"> 提供引入
浏览器按需请求模块
Vite服务器拦截请求，按需编译并提供模块

2. 高效的热模块替换HMR
实现基础：基于原生 ESM
模块更新流程：Vite服务器精确识别 HMR 边界。
             通知浏览器仅重新请求被修改模块及少数相关模块。
             浏览器利用自身模块机制更新。
3. 依赖与构建与esbuild
背景：处理第三方库（CommonJS/UMD格式，或含大量小模块的库如loadash-es）
解决方案：Vite首次启动时使用esbuild（Go编写，速度极快）进行依赖与构建
主要目的：格式转换：将非ESM依赖转换为ESM
         性能优化：将大型依赖内部众多小模块打包成单一模块
小结：原生ESM按需服务：开发时不打包，浏览器按需请求
     esbuild强力加持：依赖预构建，转换格式并优化请求

vite相比webpack快在哪里？
1. 开发服务器启动速度
2. 热模块更新（HMR）效率
3. 核心机制差异（不打包 vs 先打包）
4. 依赖预构建（esbuild）
5. 生产构建策略（Rollup）

生产构建为何用Rollup而非esbuild?
esbuild 核心优势：
使用Go语言编写
极致的构建速度（非常适合开发阶段的预构建和代码转换）
Rollup 在生产构建的优势：
使用JavaScript语言编写
生成高质量、充分优化的 JS Bundle
Vite的权衡：开发时使用 esbuild, 生产构建用 Rollup

### 5. 函数组件和类组件的本质区别
Class Component
核心机制：this关键字、生命周期方法、状态管理、组件实力
Funtional Components
核心机制：就是一个函数、没有this、Hooks

本质区别：
类组件需要实例化，基于this管理状态和生命周期；函数组件是纯函数执行，通过闭包和Hooks实现同样的能力。函数组件轻量，避免了 this 带来的心智负担，
也是 React 未来的发展方向。

函数组件和Hooks这么好，类组件还有存在的必要吗？
需要，理由如下：
1. 错误边界（类组件中的两个生命周期方法 getDerivedStateFromError和componentDidCatch）
2. 维护旧项目
3. 某些旧的第三方库可能尚未完全兼容 Hooks
4. 需要访问某些特定的、只有类组件才有的生命周期方法（不常见）

### 5. React Props 的不可变性
核心概念：什么是 Props?
Props是父组件向子组件传递的数据或指令。
组件间通信方式：数据从上往下，单向流动。

核心概念：什么是"不可变性"
1. 子组件接收到 Props 之后，不应该直接修改它
2. Props对象："只读文件"，子组件可以读取，但不能涂改
3. 父组件数据变化，传递全新的Props给子组件

面试中如何阐述 Props 不可变性的重要性
1. 重要性1：保障清晰的单向数据流
React核心设计：推崇单向数据流
如果子组件可随意修改Props: 数据来源将变得混乱
Props不可变性确保：数据流向清晰、可预测
优势：当出现问题时，更容易顺着数据流找到问题根源

2. 重要性2：性能优化的关键-浅比较
通过比较新旧Props和State来决定组件是否重新渲染
父组件数据更新时，会传递一个全新的Props对象（引用地址不同）
浅比较：比较新旧 Props 对象的内存地址是否相同
结论：不可变性使 React 的"调和"过程更高效

3. 重要性3：提升组件的可预测性与调试效率
Props不可变：组件行为更易预测
调试更简单：明确子组件内部不会偷偷修改Props
问题定位：若界面显示异常，可明确地判断时父组件 Props 传递问题，还是子组件自身 State 管理问题

4. 重要性4：便于追踪变化和实现高级功能
复杂场景应用：如实现撤销/重做功能
状态管理库（如 Redux）: 不可变性使其更容易追踪状态变更历史
核心：每次数据变化都产生新的数据对象，而非在原有对象上修改，便于记录和回溯

总结Props不可变性的重要性
1. 保障单向数据流：清晰、可预测，简化数据追踪与状态管理
2. 性能优化基础：通过浅比较高效判断组件是否需要渲染，避免不必要的深比较
3. 提升组件可预测性：简化调试，明确数据变化来源
4. 利于高级功能：如状态历史追踪、时间旅行调试等

### 6. useState的函数式更新有什么好处？
useState直接设置可能导致过时闭包问题，快速连续事件
过时闭包：Hook函数（useState、useEffect）连续触发事件因依赖数组缺失，捕获了旧的 state/props 值，导致后续渲染中函数内部使用的任时初始值
函数式更新写法如下：可以避免闭包过时问题
```javascript
function App(){
    const {count, setCount} = useState(0)
    const handleIncrementAsync = () => {
        // stale closure 过时闭包问题 连续点击两次只会执行一次 +1 
        // setTimeout(() => setCount(count+1))
        
        // 修复过时闭包问题
        // 1. 获取最新状态
        // 2. 原子性、准确性
        setTimeout(()=>{
            setCount((prevState) => {
                return prevState + 1;
            })
        }, 1000)
    }
}
```

### 7. useEffect 和 useLayoutEffect

useEffect: 异步执行
- 用于处理获取数据、订阅、手动 DOM 更改等副作用
- 核心特点(执行时机)：在浏览器布局和绘制之后异步执行（不会阻塞绘制）- DOM更细后、绘制后执行
- 好处：不阻塞浏览器渲染，应用更流畅

useLayoutEffect: 同步执行
- 与"layout"(布局)紧密相关
- 核心特点：同步执行 -- 用于 DOM 操作后、绘制前执行
- 注意：会阻塞浏览器绘制过程
- 好处：避免"闪烁"，用户直接看到最终调整好的结果

useEffect的典型场景
- 更通用，大部分副作用操作优先使用
- 场景：数据请求、事件监听、非严格绘制前 DOM 操作
- 目的：避免阻塞渲染，提升用户体验

useLayoutEffect 的典型场景
- 主要用于需要在浏览器绘制前同步完成的DOM操作
- 场景：读取DOM布局信息并同步更新 DOM(如动态计算 Tooltip 位置)
- 目的：避免用户看到视图闪烁

性能考量与经验法则
- 经验法则：优先使用 useEffect
- 仅当 useEffect 导致视觉闪烁，且操作确需绘制前完成时，才考虑 useLayoutEffect
- 注意：useLayoutEffect 同步执行，滥用易引发性能问题

useEffect 函数依赖项特性探讨
- 提供一个空数组 '[]':effect 只会在组件首次挂载（mount）后执行一次，其返回的清理函数会在组件卸载（unmount）时执行一次
- 提供一个包含依赖项的数组'[dep1, dep2]':首次挂在后执行，后续每一次渲染后，React 会使用 'Object.is()'算法比较数组中每一个依赖项的当前值
  和上一次渲染的值

useEffect 函数更新相关优化手段：
- 依赖项是函数：useCallBack:
  useCallback的主要作用是缓存函数，让React在组件重新渲染时，尽量复用上一次渲染定义的同一个函数引用，而不是创建一个新函数。
  示例：
  ```javascript
  import { useCallback } from 'react'
  function SearchComponent({ initialQuery }) {
      const [query,setQuery] = useState(initialQuery)
      const fetchResults = useCallback((currentQuery) => {
          console.log('Fetching for')
      }, [])
  
      useEffect(() => {
          if(query){
              fetchResult(query)
          }
      }, [query, fetchResults])
  
      return <input type="text" value={query} onChange=(e => setQuery(e.target.value))></input>;
  }
  ```
- 依赖项是复杂对象或数组：useMemo
  useMemo 的主要作用时缓存计算结果。当组件重新渲染时，它会复用上次计算的值，只有在依赖项发生变化时重新计算。它的核心价值在于跳过昂贵的计算，
  避免在每次渲染时重复执行，从而提升性能。
- dispatch 函数：引用是永久稳定的，所以可以安全地把它们加入依赖项数组

面试：面试中如何解释 useEffect 与 async?
问：useEffect 回调可以时 async 吗？为什么？
答：不可以， async 函数隐私返回 Promise。会导致useEffect运行错误，或者非预期行为。

面试：如何在 useEffect 中正确执行异步？
问：如何在 useEffect 中执行异步操作，比如获取数据？
答：在回调函数内部定义一个 async 函数，然后立即调用它。确保 useEffect 本身接收的直接回调同步，并关注竞态条件。
